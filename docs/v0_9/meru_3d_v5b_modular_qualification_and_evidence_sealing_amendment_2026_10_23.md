## 2. Gate governance: one question, one bounded qualification

1. **Gate charter first.** Before work on gate `Gn`, approve a versioned, additive scope charter stating the *single independently decidable question*, allowed source/dependency hashes, exact APIs/files in scope, planned adversaries and oracle, acceptance and refusal criteria, resource/environment envelope, time/compute bounds, owner/reviewer roles, immutable fixtures, outputs and `STOP` rules. Preserve an exact signed charter identity. This methodology amendment is **not** a substitute for those future charters.
2. **Separate roles.** The developer may create a *candidate* correction or instrument component in an isolated working tree only after that gate's specific development authorisation. The independent reviewer must seal mathematical expectations and the hostile-test design **before inspecting that gate's candidate changes**. Reviewers cannot fix developer source, delete failures or quietly tune tests to pass. Any material correction after a reviewer finding requires a new versioned developer candidate, a preserved negative result and renewed independent review of the affected scope.
3. **Fixture-first and non-importing QC.** Predeclare/hash representative and adversarial fixtures and expected outcomes; explicitly distinguish additional exploratory attacks. Review proof/certificate soundness with an independently developed oracle and arithmetic backend, never by importing the producer/validator/Claude checker as the authority. A reviewer may call the subject under test *only* in a clearly labelled adversarial interface suite.
4. **Acceptance is scoped.** Gate decisions are `PASS_SCOPE_LIMITED`, `FAIL`, `INCOMPLETE`, `BLOCKED`, or `EVIDENCE_LOSS_STOP`. A developer may say only `READY_FOR_INDEPENDENT_QC` with limitations. `PASS_SCOPE_LIMITED` is **not** `SEALED`. A human-signed *gate-seal* referencing complete independent evidence and dependency hashes is needed to promote that exact scope to `SEALED`. Failure, incomplete review, unsupported host or missing evidence prevents sealing; no fractional/majority pass logic.
5. **Separate subclaims rather than mute failures.** Within a gate, independently proved parts may be catalogued as `SUPPORTED_SCOPED_EVIDENCE`, but an unresolved critical requirement prevents a whole-gate seal. Historical signed reports, all old and new negative evidence, and original unqualified statuses remain append-only.
6. **No auto-progression.** Signing a gate seal makes its specified claim available for citation as a prerequisite; it never approves a subsequent gate, implementation freeze or scientific run. Each next action needs explicit human authorisation.

## 4. Dependency DAG, inheritance, invalidation and change control

Minimum directed dependencies: **G0 → G1,G2,G4**; **G1+G2 → G3**; **G0+G2 → G5**; **G1+G2+G3+G4+G5 and G0 → G6**. Gate chronology may follow the default linear order even where DAG edges permit independent work. Passing some prerequisites never waives other prerequisites. A cross-cutting change to parsing, logging, accounting or execution infrastructure can invalidate multiple sealed gates even when their tests were historically green.

Every gate must publish a *dependency closure manifest* with exact SHA-256s of the qualified entrypoint, imported source modules, validator/checker interfaces, schema/fixtures, environment and toolchain, plus explicit assumptions about kernel, procfs/cgroups and trust in arithmetic libraries. Declare both: (i) the hash and mathematical identity of each *claim*; and (ii) its *implementation/dependency fingerprint*. A downstream gate cites a prior seal by its exact signed Git commit, content hash and accepted scope—not by a mutable path, informal summary or model-generated PASS text.

**Reuse is conditional, never automatic:**

- Unchanged code and dependency hashes **plus** unchanged declared assumptions allow reference to a prior sealed claim without routinely repeating its full bounded proofs. Verify the identity and interface contract before reuse; reuse covers only the original claimed scope.
- Any modification of a gate's transitive dependencies, serialization schema, parser, CPU ledger, proof rule, independent oracle trust basis, or required runtime assumptions triggers a documented *impact analysis before execution*. Affected gates become `SEAL_SUSPENDED_PENDING_REQUALIFICATION`; do not quietly inherit or overwrite their previous seals.
- If a purportedly independent unaffected component can be shown truly hash-identical, record the proof of nonimpact with the exact dependency cut. The human may approve scoped requalification; blanket "all previous gates still pass" is not evidence.
- A new counterexample, failed hostile test, contradictory theorem, invalid external assumption or integrity mismatch overrides a prior green label for new use: stop dependent work, preserve the original sealed event, sign a new incident/amendment where applicable, and requalify explicitly. **Never erase the historic seal**; record its superseded/suspended status with an additive signed note.
- `R2-F05` missing historical logs are a permanent historic limitation. New prospective executions must be fully logged; they may not be described as reconstructions of lost historical runs.

## 5. What constitutes a verifiable evidence seal

For each gate publish (a) a complete, immutable **external evidence ZIP** and (b) a small **human-reviewed, GPG-signed additive gate-seal Markdown record** in Git pointing to that ZIP by exact SHA-256/byte length and verified durable retrieval location. Do **not** commit large evidence ZIPs to the signed scientific branch merely to obtain a Git identity. The gate seal must state:

1. Gate identifier/version, exact signed gate charter, human authorisation date, developer candidate version, independent reviewer and independence restrictions.
2. Exact prior signed-parent commit and preserved historical protocols/reviews; all required prior signed gate seals and their statuses.
3. Precisely accepted **claim/theorem/software interface**, allowed inputs, expected outputs, exclusions, formal assumptions and bounded test scope.
4. Full transitive code/dependency/toolchain/OS capability fingerprints, signed resource constraints and interface-specific hashes; no mutable "latest" references.
5. Fixture-first frozen register and independent oracle design seal, hostile families, exact tests, proof artifacts, commands, stdout/stderr, exit codes, environment and both successful **and negative** evidence.
6. Complete QC matrix with `PASS_SCOPE_LIMITED`, `FAIL`, `INCOMPLETE`, `BLOCKED`, `EVIDENCE_LOSS_STOP` and explicit waived/not-attempted fields (no silent skips); finding owner, severity, counterexample hashes and assumptions.
7. Durable checkpoint chain and fresh independent readback receipt, including outer archive SHA-256, all member hashes, safe extraction, predecessor linkage and separately retained irreversible negative evidence.
8. Dependency graph and unambiguous *permitted downstream use*, invalidation triggers, stop conditions and limits on claims; reviewer/source conflicts disclosed.
9. A **separate explicit human signature decision** `GATE_SEALED_SCOPE_LIMITED` or `GATE_NOT_SEALED`, which is not delegated to the developer or reviewer and must correspond to supported independent evidence.

After every substantial bounded batch make a recoverable checkpoint before relying on an ephemeral agent workspace. The first and final checkpoint must be freshly retrieved and SHA-256 verified from durable storage; intermediate checkpoint receipts must identify exactly what was/was not actually verified. If Project storage is exhausted, use an independently retrievable external artifact/Library location with a verified readback rather than deleting prior evidence. Interrupted tests preserve partial logs and report incomplete; **essential evidence-loss triggers `EVIDENCE_LOSS_STOP`**, followed by a separate prospective recovery authorisation. No reconstruction may masquerade as the original run.

## 6. Separation of gate charters, developer work, independent QC and sealing

The default lifecycle for **each gate** is:

`SIGNED FRAMEWORK` → `SIGNED / EXPLICIT HUMAN GATE CHARTER AND WORK AUTHORIZATION` → `FROZEN TEST EXPECTATIONS + HOST CAPABILITY PRECHECK + BASELINE CHECKPOINT` → `ISOLATED DEVELOPER CANDIDATE (IF NEEDED)` → `SEPARATE INDEPENDENT QC` → `FULL ARCHIVE + FRESH READBACK` → `HUMAN GATE-SEAL DECISION` → `OPTIONAL SEPARATELY AUTHORISED NEXT GATE`.

A single agent may not both implement and independently certify the same corrected source. If a gate is mathematical/read-only, omit the development substage and preserve that limitation. Independent tests must remain predeclared against the candidate where possible; newly discovered attacks are legitimate findings but cannot retroactively be represented as preregistered fixtures. Any material host substitution is recorded and may require a new environment qualification. A non-PASS gate is a valid scientific outcome; nothing is repaired automatically, reclassified through time tolerances or silently moved to G6.

If a gate needs more time than one bounded session, the executing agent must prioritise signed-scope compliance and independently verified checkpoints over uninterrupted work. An external store survives only if a fresh reconstruction from that store was actually validated. Strict elapsed credit constraints are execution logistics, **never reasons to weaken verification**.
